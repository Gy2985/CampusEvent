# 设计模式决策报告（v2 补充章）

> 本文件是 v1《05-设计模式决策报告.md》的**增量补充**，不重复 v1 已写内容。
> 只回答两个问题：**CR-01 为什么用"独立策略"而不是"组合规则"**、**CR-02 为什么用"端口 + 观察者"**。

## 1. CR-01：年级限定为什么是"再加一个策略"

### 1.1 判断依据：这条规则会不会变？

| 规则 | 会不会变 | 依据 |
| --- | --- | --- |
| 名额上限 | 不变（所有活动都有） | 公共约束，服务层统一执行 |
| 活动开始时间 | 不变 | 同上 |
| 不允许重复有效报名 | 不变 | 同上 |
| **谁有资格报名** | **会变**（今天是年级，明天可能是专业/学号段/会员等级） | 因此归入"策略"，是变化点 |

把"会变的"留在策略、把"不变的"留在服务层，是初始设计就已经定下的边界；CR-01 只是验证了这个边界确实好用。

### 1.2 为什么不是"组合规则（装饰器链条）"

教师材料明确写了"可通过新增独立策略实现，或采用可组合规则设计，但应解释设计选择"。我选择独立策略，理由三条：

1. **规则数量**：当前只有 1 条资格规则。为一个规则引入"组合器 + 规则链"抽象，是典型过度设计——
   评审成本、调试成本都要翻倍，换来的只有"未来可能加规则"的想象。
2. **继承公共约束的代价**：独立策略天然只关心"资格 + 目标状态"，其余三条公共约束由服务层兜住；
   组合器则要额外定义"短路顺序"（名额先查还是资格先查），这类顺序问题在需求里没有答案，容易变成争论点。
3. **测试成本**：独立策略可以用一个不可变的 `RegistrationContext` 直接单测；组合器需要构造整条链。

**保留的演进路径**：如果将来出现第二条资格规则（例如"年级 + 专业"），
再加 `CompositePolicy([GradeRule, MajorRule])`，让 `GradeLimitedDirectPolicy` 变成其中一条规则即可，
策略的 `decide()` 契约不变——这是"现在不过度设计、但也不挡未来"的典型处理。

### 1.3 拒绝方式为什么是"抛异常"而不是"返回 REJECTED 决策"

`RegistrationDecision` 的语义是"这条报名应该以什么状态落库"。年级不符时**不应该落库**，
所以返回 `REJECTED` 会带来三个副作用：污染报名名单、与"重复报名"规则冲突、把"审批拒绝"
和"资格拒绝"混成同一个状态。用 `GradeRestrictedError` 让事务回滚，语义更干净。

这也顺带说明一件事：**策略不只要能"决定状态"，还要能"拒绝提交"**。
如果将来策略越来越多，这个契约（`decide` 可抛出业务异常）需要写进 `policies/base.py` 的文档里——
本次已在类注释中写明。

## 2. CR-02：邮件为什么是"端口 + 观察者"，而不是"服务里加一行 send"

### 2.1 依赖方向

```
RegistrationService ──发布事件──> EventBus ──通知──> {NotificationObserver, EmailNotificationObserver}
                                                            │
                                                            └─依赖端口─> EmailSender <──实现── MockEmailSender
```

服务层**不知道**邮件存在，这是关键：报名这件事的正确性不应该取决于"邮件服务器在不在"。

### 2.2 三个替代方案为什么不选

| 方案 | 问题 |
| --- | --- |
| 在 `register()` 里直接 `send_mail()` | 报名成功与否被外部服务绑架；要写 `try/except` 包裹，等于把渠道故障处理塞进业务核心；测试要连 SMTP 或打桩 |
| 在 `NotificationObserver` 里顺便发邮件 | 站内通知与邮件耦合在一个类里，任一渠道故障互相牵连；"一个观察者只负责一个渠道"的边界被破坏 |
| 直接 `import smtplib` | 教学环境连不上真实 SMTP；换实现要改观察者，端口隔离的意义丢失 |

### 2.3 端口（`EmailSender`）的价值

* **可注入故障**：`MockEmailSender(always_fail=True)` 让 CR2-03 可以真的跑到"发送失败"分支，
  而不是靠人嘴说"我们处理了失败"。
* **可替换**：生产环境写 `SmtpEmailSender(EmailSender)`，`create_app` 换一行即可。
* **可断言**：Mock 内部记录 `outbox`，测试能直接看"到底发了什么"。

### 2.4 幂等模式的选择

站内消息用的是"`INSERT OR IGNORE` + 唯一键"，邮件沿用了同一套思路，但多做一步"先占位（QUEUED）再完结（SENT/FAILED）"：

* 只 `INSERT OR IGNORE` 再发送，如果发送过程崩溃，库里会留下一条"看起来已发"的记录，无法区分；
* 先占位则能区分"没发"（无记录）/ "正在发"（QUEUED）/ "已发"（SENT）/ "失败"（FAILED），
  也便于管理端做"失败重发"。

## 3. 结论

| 变更 | 命中扩展点 | 核心服务改动 | 新增实现 |
| --- | --- | --- | --- |
| CR-01 | 策略模式 | 0 行 | 1 个策略类 |
| CR-02 | 观察者模式 | 0 行 | 1 个观察者 + 1 个端口 + 1 个 Mock 适配器 |

两个变更都没有触碰 `RegistrationService` 与 `EventBus`。这并不是"运气好"，
而是初始设计时就把"会变的规则/渠道"和"不变的业务事实"分开的回报。
