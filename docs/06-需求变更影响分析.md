# 实验二 · 需求变更影响分析（CR 待发布）

> 状态：**等待教师发布变更单（CR）**。
> 依据 3.6 节：初版验收后由教师统一发布 CR，在此之前不得获取或提前实现变更功能。
> 本文档先把“分析方法与模板”固化下来，CR 到手后 24 小时内填完第 2 节并给出影响面清单。

## 1. 分析方法（拿到 CR 后的固定动作）

1. **拆规则**：把 CR 拆成“新增规则 / 修改规则 / 删除规则”，逐条编号（CR-01、CR-02…）。
2. **定位规则归属**：用 `01-需求分析与设计边界.md` 第 4 节的对照表，看这条规则当前落在哪个类。
3. **判断影响面**：按层往下走一遍，逐层写“要不要改、为什么”。
4. **判断是否越界**：若 CR 需要改动 3 个以上核心类、或需要改动策略接口签名，先停下来复核设计是否被 CR 推翻。
5. **先补测试再改代码**：新增用例先写成失败状态（红），再让 AI 改到绿。
6. **回归**：C1–C10 + X 系列全部重跑，记录失败项与原因。

## 3. 预判：哪些 CR 会“便宜”，哪些会“贵”（基于当前设计）

这不是对具体 CR 的猜测，而是对设计弹性的自评，供变更时对照。

| CR 类型（举例方向） | 预期影响面 | 为什么 |
| --- | --- | --- |
| 新增一种报名规则（如抽签/邀请制） | 小：新增 1 个策略类 + 注册 1 行 + 表单/枚举各加 1 个取值 | 策略抽象稳定，`RegistrationService` 不动 |
| 修改某类活动的名额计算口径（如候补） | 中：改 `RegistrationContext` / `count_by_status` 的调用方式，可能新增状态 | 名额是公共规则，集中在一处，改点少但影响所有活动 |
| 新增通知渠道（邮件/企业微信） | 小：新增 1 个观察者 + `subscribe` 一行 | 事件已与投递解耦 |
| 修改通知文案或增加“已读回执” | 小~中：改文案构造处 / 扩 `Message` 表字段 | 消息模型简单，但涉及表结构 |
| 引入“活动取消/改期” | 中~大：新增状态与迁移、补通知事件、补测试 | 状态机会变复杂，需要重新画状态图 |
| 权限细化（按院系审批） | 大：`Role` 模型要扩，服务层身份校验要重构 | 当前只有 student/admin 两种角色，属于设计边界外的扩展 |

## 4. 变更期间的过程要求（自查清单）
