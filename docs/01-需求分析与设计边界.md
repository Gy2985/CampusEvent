# 实验二 · 初始需求分析与设计边界

> 依据：指导书 3.2 节、附录 B.1 / B.2 / B.3
> 产出目的：把“业务规则”落到“谁负责实现”，为后续类图与模式选择提供依据。

## 1. 一句话需求

校园管理员发布活动，学生浏览并报名；报名分“直接报名”和“管理员审核”两类，报名与审核结果通过站内消息通知学生。

## 2. 范围

| 做 | 不做 |
| --- | --- |
| 活动增删改查、按名称筛选 | 账号注册、密码与复杂权限体系（使用固定演示账号） |
| 报名、取消、审核（批准/拒绝） | 消息队列、短信/邮件推送 |
| 四类报名状态与状态机约束 | 移动端 App、复杂日历、支付 |
| 站内消息通知 | 多租户、分布式部署 |
| 名额与统计（已通过数、待审核数、剩余名额） | 软删除（本版选择“有报名记录则拒绝删除并提示”） |

## 3. 角色与数据

| 角色 | 说明 | 能做什么 |
| --- | --- | --- |
| Student | 学生（S001~S003 演示账号） | 浏览/筛选活动、报名、取消、查看我的报名与消息 |
| Admin | 管理员（A001 演示账号） | 创建/编辑/删除活动、批准/拒绝待审核报名、查看统计 |

| 对象 | 关键字段 | 约束 |
| --- | --- | --- |
| Student | student_id、name、role | student_id 唯一；role 限定 student/admin |
| Activity | activity_id、title、category、start_at、location、capacity、policy_type | capacity 为正整数；开始后不接受新报名 |
| Registration | registration_id、activity_id、student_id、status | status ∈ {待审核, 已通过, 已拒绝, 已取消}；同活动同学生最多一条有效记录 |
| Message | message_id、student_id、activity_id、content、is_read、dedupe_key | 同一业务事件只能产生一条消息（幂等键唯一） |

## 4. 业务规则 → 实现位置 → 验证用例

这条对照表是本项目的“可追踪性矩阵”：每条规则都能指到一个类和一个测试。

| 规则（B.2 编号） | 规则内容 | 实现位置 | 验证用例 |
| --- | --- | --- | --- |
| 1 | 直接报名：名额充足即“已通过”，并产生通知 | `DirectRegistrationPolicy.decide` + `RegistrationService.register` | C2 |
| 2 | 审核型：提交为“待审核”，批准后“已通过”并通知 | `ApprovalRegistrationPolicy.decide` + `RegistrationService.approve` | C5、C6 |
| 3 | 名额只按“已通过”算；待审核不占名额；满员不得批准 | `RegistrationRepository.count_by_status` + `RegistrationService.approve` | C8、X9 |
| 4 | 同活动同学生不得有两条有效报名；已拒绝/已取消可再申请 | `RegistrationService.register` + 数据库部分唯一索引 | C3、X10 |
| 5 | 学生可取消自己的待审核/已通过报名；活动开始后不得报名 | `RegistrationService.cancel` / `register`（时间校验） | C9、X1、X2 |
| 6 | 通知失败要留痕，但不得让已合法提交的报名消失 | 事务提交后发布事件 + `NotificationObserver` 失败写入 `notification_failures` | X7 |
| 7 | 活动与报名必须持久化；删除有报名的活动需说明策略 | SQLite 落库；`ActivityService.delete` 拒绝删除并提示 | C10、X5b |

## 5. 需求中的模糊点与设计决策

这些是“需求没写死、必须由学生决定”的地方，决策理由记录在此，代码注释与报告保持一致。

| # | 模糊点 | 可选做法 | 本版决策与理由 |
| --- | --- | --- | --- |
| D1 | 名额检查放策略里还是服务里？ | ①放进每个策略；②放服务层统一 | **放服务层**。名额上限是两类活动共有的约束，属于“公共规则”；策略只回答“进入哪个状态”，并通过 `requires_immediate_capacity_check` 声明是否需要提交即校验。避免策略间重复代码，也避免服务里写类型判断。 |
| D2 | 满员后审核型活动还能不能提交申请？ | ①直接拒绝；②允许排队，批准时再拦 | **允许排队**。B.2 第 3 条明确“待审核不占名额”，若提交即拒绝，会与“批准时复查名额”的设计矛盾，也让学生失去候补机会。 |
| D3 | 删除已有报名的活动怎么办？ | ①拒绝删除；②软删除；③级联删除 | **拒绝删除并提示**。数据量小、演示项目不需要软删除字段；级联删除会破坏历史报名记录，风险最大。 |
| D4 | 通知失败是否回滚报名？ | ①回滚；②不回滚但留痕 | **不回滚 + 留痕**。报名本身合法，通知属附属动作；回滚会让用户以为没报上，而消息又发不出去，责任不清。 |
| D5 | 如何避免重复通知？ | ①在观察者里查重；②靠业务代码不重复发布；③幂等键 | **幂等键**（`event_type:registration_id` 唯一索引 + `INSERT OR IGNORE`）。成本最低、对调用方无要求，重复发布天然被吸收。 |
| D6 | 学生取消已通过的报名，名额如何变化？ | ①不变；②立即释放 | **立即释放**：统计按“已通过”实时计算，取消后剩余名额自动 +1，无需额外补偿逻辑。 |
| D7 | 管理员账号能否报名？ | ①可以；②不可以 | **不可以**（服务层抛出 `PermissionDeniedError`）。角色语义不同，避免“审批自己报名”的荒唐场景。 |

## 6. 报名状态机

```
            register(直接报名, 有名额)
   (无记录) ──────────────────────────▶ 已通过
        │                                  │
        │ register(审核型)                 │ cancel
        ▼                                  ▼
     待审核 ──approve(有余位)──▶ 已通过   已取消
        │                                  ▲
        │ reject                           │ cancel
        ▼                                  │
     已拒绝                             (待审核/已通过)

非法迁移：已拒绝→取消、已通过→再批准、已取消→批准，均抛 InvalidStateTransitionError
```

## 7. 非功能约束（本版如何满足）

| 约束 | 措施 |
| --- | --- |
| 数据一致性 | 报名/审批使用 `BEGIN IMMEDIATE` 显式事务；关键约束有 CHECK 与部分唯一索引兜底 |
| 可测试性 | 领域层不依赖 Flask/SQLite 会话，服务层注入 `Database`，36 条 pytest 用例可直接驱动 |
| 可维护性 | 分层 + 策略 + 观察者，新增报名方式/通知渠道不需要改主流程 |
| 可运行性 | README 给出从零安装、初始化、启动、测试命令；首次启动自动建库 |
| 输入安全 | 所有表单经服务层校验（名称长度、容量正整数、时间格式、报名方式枚举）；ORM 层使用参数化 SQL，无拼接 |
