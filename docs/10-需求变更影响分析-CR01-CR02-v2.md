# 需求变更影响分析（CR-01 / CR-02）· v2

> 文档版本：**v2**（v1 为初始版本的《06-需求变更影响分析.md》，未修改）
> 分析对象：教师材料《实验二教师专用材料》中的 CR-01（年级限定报名）与 CR-02（模拟邮件通知）
> 分析时机：baseline-v1 已验收并打标签之后、动手改代码之前
> 分析者：学生（独立完成本节；AI 仅用于辅助实现与测试，见 `AI_DEV_LOG.md`）

---

## 0. 变更摘要与共同前提

| 编号 | 变更 | 一句话本质 |
| --- | --- | --- |
| CR-01 | 新增"年级限定直接报名" | 报名**规则**多了一条：资格判定从"谁都能报"变成"仅大二/大三" |
| CR-02 | 新增 Mock 邮件通知 | **通知渠道**从一个变成两个，且要求失败隔离 + 幂等 |

两个变更正好分别落在本系统初始设计的两个"可扩展点"上：

* CR-01 落在**策略模式**（`RegistrationPolicy`）；
* CR-02 落在**观察者模式**（`EventBus` + 观察者）。

这也是初始设计的价值所在：变更不是"推翻重做"，而是"在既有扩展点上加一个实现"。

## 1. CR-01 影响分析：年级限定直接报名

### 1.1 需求拆解

把 CR-01 的一句话需求拆成可判定条目：

| 条目 | 判定方式 | 归属 |
| --- | --- | --- |
| 仅 `grade ∈ {2,3}` 可报名此类活动 | 报名前资格判定 | **新规则（策略）** |
| 其他年级"收到明确提示" | 抛出可被 Web 层转成提示的业务异常 | 新规则（策略） |
| 仍受名额上限约束 | 服务层公共规则 3 | 公共约束（不动） |
| 仍受"活动已开始不可报名"约束 | 服务层公共规则 1 | 公共约束（不动） |
| 仍受"不允许重复有效报名"约束 | 服务层公共规则 2 | 公共约束（不动） |
| 原有直接报名 / 审核报名行为不变 | 回归 C1–C10 | 回归范围 |

结论：**"名额、时间、重复"三条是公共约束，"年级"是新增的可变规则**。把年级写进服务层主流程，
就等于把一条会变的规则变成服务层的一部分——与初始设计的分层原则冲突。

### 1.2 受影响构件（改动清单）

| 文件 | 职责 | 改动类型 | 风险 |
| --- | --- | --- | --- |
| `domain/entities.py` | 实体与枚举 | `PolicyType` 增 `GRADE_LIMITED`；`Student` 增 `grade` | 低（纯数据） |
| `domain/errors.py` | 业务异常 | 新增 `GradeRestrictedError` | 低 |
| `policies/implementations.py` | 报名策略 | 新增 `GradeLimitedDirectPolicy` 并登记 | 低 |
| `schema.sql` | 表结构 | `students` 增 `grade`；`activities.policy_type` 校验放宽到三值 | **中**：SQLite 不能修改 CHECK，需重建表 |
| `db.py` | 初始化/迁移 | 新增 `upgrade()`：老库补列 + 重建 activities | **中**：迁移失败会污染库 |
| `repositories/student_repository.py` | 学生仓储 | SELECT/映射补 `grade` | 低 |
| `services/activity_service.py` | 活动校验 | 报名方式白名单加一项 | 低 |
| `web/*` + `templates/*` | 页面 | 活动表单下拉项、资格提示、登录页显示年级 | 低 |
| `db.py::_seed_demo_data` | 演示数据 | 学生补年级 + 一条年级限定活动 | 低 |

**明确不改**：`RegistrationService.register/cancel/approve/reject` 的方法体、事务边界、事件发布时机、
`RegistrationStatus` 状态机、`EventBus`。

### 1.3 三种方案对比与选择

| 方案 | 做法 | 优点 | 代价 | 结论 |
| --- | --- | --- | --- | --- |
| A 新增独立策略 | 新增 `GradeLimitedDirectPolicy`，`policy_type=GRADE_LIMITED` | 服务层零改动；规则自洽可单测；与既有策略平级、易理解 | 新增一种 policy 取值（要改 schema 校验与下拉框） | **采用** |
| B 可组合规则 | 用装饰器把"资格校验"叠在 `DirectRegistrationPolicy` 上 | 未来多规则组合更灵活（年级 + 专业 + 会员） | 需要引入规则链/组合器抽象，当前只有一条规则，属过度设计；排错链路变长 | 不采用，但在文档中保留演进说明 |
| C 服务内 if | 在 `register()` 里 `if policy==GRADE_LIMITED and grade not in ...` | 改动点最集中 | 把可变规则塞进核心流程；下次再来一条"专业限定"就得继续加 if | 不采用 |

为什么选 A 而不是 B：本系统只有"直接报名""审核报名"两种策略，CR 只加一条资格规则；
一条规则用组合器包装，抽象成本高于收益。A 的代价只是"多一个枚举值"，并且天然符合
`RegistrationPolicy` 的既有契约（策略只回答"报名进入哪个状态 + 给学生什么文案"）。

### 1.4 关键设计决定：拒绝 = 不创建记录，而不是写一条 REJECTED

年级不符时有两种写法：

1. 返回 `RegistrationDecision(status=REJECTED)` → 落一条"已拒绝"记录；
2. 抛 `GradeRestrictedError` → 事务回滚，**不产生任何报名记录**。

选择 2，理由：

* **与重复报名规则冲突**：若留下 `REJECTED` 记录，学生再点一次仍会被"重复报名"拦下需求之外的路径；
  而"年级不符"是可解释的、不该产生历史垃圾的拒绝。
* **状态语义**：`REJECTED` 在本系统里表示"管理员审核后不通过"，是审批结果；资格不符不是审批结果。
* **统计口径**：不产生记录 → 名额、待审核数、报名名单都不被污染。

代价：不会留下"某人尝试过但被拒"的审计痕迹。本实验无此要求；若将来要做审计，
应新增 `audit_log` 而不是复用报名状态（同样不污染核心状态机）。

实现上这个异常由策略直接抛出，穿过 `register()` 的事务回滚到 Web 层，
`register()` 的方法体**不需要任何修改**——这正是"新增策略而不修改核心服务"。

### 1.5 数据模型影响与迁移风险

* `students` 加 `grade INTEGER`（1–4，管理员为 NULL）：可用 `ALTER TABLE ADD COLUMN`，风险低。
* `activities.policy_type` 的 `CHECK (policy_type IN ('DIRECT','APPROVAL'))` 必须放宽到三值。
  **SQLite 不支持修改 CHECK 约束**，只能"建新表 → 拷数据 → 删旧表 → 改名"。
  由于 `registrations` 有外键指向 `activities`，重建时必须临时关闭 `foreign_keys`，
  否则 `DROP TABLE` 会触发约束错误。

风险与对策：

| 风险 | 对策 |
| --- | --- |
| 老库（评审机/我自己 D 盘的 `data/campus_event.db`）迁移失败 | 迁移前检测约束文本；只在确需重建时执行；失败记录日志并抛出，绝不"半迁移" |
| 重建表时外键崩溃 | 迁移在独立连接上 `PRAGMA foreign_keys=OFF` → 重建 → `ON` |
| 云端部署库是全新库 | `initialize()` 直接建新结构，迁移逻辑只在"老库"路径生效，不影响上线 |

### 1.6 回归范围

* C1–C10 全部（尤其 C2/C4/C5：直接报名、名额满、审核报名）；
* 16 条边界（时间、名额、重复、状态机）；
* 10 条界面用例（新增下拉项后表单仍可提交）；
* 新增 CR1-01 ~ CR1-05。

## 2. CR-02 影响分析：Mock 邮件通知

### 2.1 需求拆解

| 条目 | 判定方式 | 归属 |
| --- | --- | --- |
| 站内通知继续运行 | 现有 `NotificationObserver` 不动 | 既有渠道（不动） |
| 报名通过 / 审核通过 / 审核拒绝 有邮件 | 邮件观察者按事件类型过滤 | 新渠道 |
| 记录收件人、主题、正文、状态、时间 | `email_outbox` 表 | 新基础设施 |
| 发送故障必须记录错误 | 行内 `status=FAILED` + `error` + 日志 | 新渠道 |
| 故障不得回滚已成功提交的报名 | 邮件在事务提交**之后**由事件分发；观察者吞掉异常 | 既有事务设计已满足 |
| 同一业务事件不得重复发送 | 幂等键唯一索引 | 新渠道 + 复用 `dedupe_key` |
| 不把邮件代码写进 `RegistrationService` | 观察者订阅事件 | 架构约束 |

### 2.2 受影响构件

| 文件 | 改动 |
| --- | --- |
| `ports/email_sender.py`（新） | `EmailSender` 端口 + `MockEmailSender` 适配器（可注入失败） |
| `observers/email_notification_observer.py`（新） | 订阅事件 → 组装邮件 → 幂等校验 → 发送 → 落库 |
| `repositories/email_repository.py`（新） | `email_outbox` 的占位/完结/查询 |
| `schema.sql` + `db.py` | 新表 `email_outbox`（幂等键 UNIQUE） |
| `__init__.py` | 装配：`EmailSender` 实例 + 订阅观察者 |
| `web/admin.py` + 模板（新） | 管理端"邮件记录"页 |
| `events/event_bus.py` | 不动（已是多观察者结构，异常隔离已就绪） |
| `services/registration_service.py` | **不动** |

### 2.3 为什么"观察者 + 端口"，而不是在服务里调 send_email

* 服务层的职责是"保证报名这条业务事实正确"；发邮件是**副作用**，失败不应影响业务事实。
* 若写进服务，就得在服务里 `try/except` 包裹、还要判断"这条事件该不该发邮件"——
  等于把渠道策略塞进业务核心，正是初始设计要避免的耦合。
* 用端口（`EmailSender`）而不是直接 `smtplib`：教学环境要 Mock，生产要真实 SMTP，
  替换实现只改装配、不改观察者。这就是"依赖倒置"的落地。

### 2.4 幂等键与并发

* 键：`EMAIL:{event_type}:{registration_id}`，复用事件对象已有的 `dedupe_key`，加渠道前缀避免与站内消息撞键。
* 实现顺序：**先占位再发送**——`INSERT`（`status=QUEUED`，`dedupe_key` 唯一）成功才发送，
  发送结果再 `UPDATE` 成 `SENT/FAILED`。这样即使同一事件被重复分发（例如未来重放），
  第二次 `INSERT` 直接被唯一索引拒绝，天然防重复。
* 不用"先查后插"：那有并发窗口；唯一索引是数据库层的最后防线。

### 2.5 失败语义

| 场景 | 站内通知 | 邮件行 | 报名记录 |
| --- | --- | --- | --- |
| 正常 | 1 条 | `SENT` | 已通过/待审核，不变 |
| 邮件发送抛异常 | 1 条（不受影响） | `FAILED` + `error` | 不回滚（早已提交） |
| 事件重复分发 | 不变（自身幂等） | 只有 1 行 | 不变 |

失败行保留 `FAILED` 作为终态，不自动重试：教学场景以"可解释、可查证"优先；
若要重试，应由管理端显式"重发"按钮触发（本实验未要求，作为演进项写进报告）。

### 2.6 事件范围

| 事件 | 是否发邮件 | 原因 |
| --- | --- | --- |
| `SUBMITTED` 且状态为 `APPROVED`（直接报名通过） | 发 | CR2-01 |
| `SUBMITTED` 且状态为 `PENDING`（审核报名已提交） | 不发 | 需求只要求"通过/拒绝"；提交本身站内已有提示 |
| `APPROVED` | 发 | CR2-02 |
| `REJECTED` | 发 | CR2-02 |
| `CANCELLED` | 不发 | 需求未覆盖，避免打扰 |

判定所需的状态**从事件中读不到**（事件是最小信息集），因此观察者按 `registration_id`
回查一次报名状态——**这是观察者对读模型的依赖，而不是让服务层为通知而改事件结构**。
（备选方案：给事件加 `status` 字段，但那等于"为渠道改领域事件"，取舍见 §4。）

### 2.7 数据模型

`email_outbox`：`to_addr / subject / body / status(QUEUED|SENT|FAILED) / error / dedupe_key(UNIQUE) / created_at`。
不记录"已发送"以外的副作用；正文存快照，便于教师验收时逐条对照。

### 2.8 风险

| 风险 | 说明 | 对策 |
| --- | --- | --- |
| Mock 与真实邮件差异 | Mock 不校验地址格式、不限流 | 端口隔离，真实实现替换时只改装配 |
| 观察者增多 | 站内 + 邮件串行分发，单条失败被 `EventBus` 兜住 | 已隔离，单点失败不影响其它观察者 |
| 回查状态多一次查询 | 每条事件 +1 次 SELECT | 单机演示规模可接受，写进性能说明 |

## 3. 实施顺序（先分析、后修改）

1. 打标签 `baseline-v1`（已完成，验收基线不可变）。
2. **本文档评审通过**（教师/评审同学看影响面是否说清）。
3. 新建分支 `change-v2`，先在分支上改代码。
4. 先做 CR-01（数据模型改动大、影响面广），跑全量回归；再做 CR-02（纯新增，风险低）。
5. 补 CR 测试 → 全量回归 → 生成 `baseline-v1..change-v2` 的差异报告。
6. 合并回 `main`，打 `change-v2` 标签，推送到 Gitee / GitHub 并重新部署。

## 4. 影响面结论

* **核心服务零改动**：`RegistrationService` 的四个业务方法体在 change-v2 中一行未改（可用 diff 证明）。
* **新增实现**：1 个策略、1 个观察者、1 个端口 + 适配器、1 张表、1 个管理页面。
* **一处结构性改动**：`activities.policy_type` 的 CHECK 约束，需 SQLite 重建表——这是本次唯一"有风险"的改动，
  也解释了为什么它对 CR-01 是必要的、对 CR-02 完全不需要。
* **一处主动取舍**：拒绝资格不符时不落 `REJECTED` 记录（§1.4）；事件不带状态、由观察者回查（§2.6）。
  两处取舍都写清理由，供评审质疑而不是"照做"。
