## 3. 关键差异（改了什么 / 没改什么）

### 3.1 报名方式从 2 值扩到 3 值

```diff
 class PolicyType(str, Enum):
     DIRECT = "DIRECT"
     APPROVAL = "APPROVAL"
+    GRADE_LIMITED = "GRADE_LIMITED"
```

### 3.2 新增策略（不改服务）

```python
class GradeLimitedDirectPolicy(RegistrationPolicy):
    policy_type = PolicyType.GRADE_LIMITED
    requires_immediate_capacity_check = True
    ALLOWED_GRADES: frozenset[int] = frozenset({2, 3})

    def decide(self, context) -> RegistrationDecision:
        if context.student.grade not in self.ALLOWED_GRADES:
            raise GradeRestrictedError("该活动仅限大二、大三学生报名，当前账号为…")
        return RegistrationDecision(status=APPROVED, student_message="报名成功…")
```

`register()` 里的三行公共规则（开始时间 / 重复报名 / 名额）**原样保留**，年级判定由策略完成。

### 3.3 通知渠道从 1 个变 2 个（并列订阅）

```python
event_bus.subscribe(NotificationObserver(db).handle)          # v1 已有
event_bus.subscribe(EmailNotificationObserver(db, sender).handle)  # v2 新增
```

### 3.4 幂等：先占位再发送

```python
reserved = EmailRepository(conn).reserve(dedupe_key=f"EMAIL:{event.dedupe_key}", ...)
if not reserved:            # 唯一索引命中 → 这次不发
    return
try:
    sender.send(...)
except Exception as exc:
    self._finish(key, "FAILED", f"{type(exc).__name__}: {exc}")   # 失败留痕
else:
    self._finish(key, "SENT")
```

## 6. 复盘：哪里顺、哪里卡

**顺的地方（说明设计起了作用）**

1. CR-01 只新增一个策略类 + 注册表一行，`register()` 完全不用碰；年级规则天然继承了
   "名额/时间/重复"三条公共约束，不需要在策略里重复写一遍。
2. CR-02 只新增一个观察者 + 一个端口；`event_bus` 早就支持多观察者，装配两行就完事。
3. 幂等直接复用了 v1 为站内消息设计的 `dedupe_key`，加渠道前缀即可，不需要另造一套。

**卡的地方（如实记录）**

1. `activities.policy_type` 的 CHECK 是 SQLite 的"硬骨头"：不能 ALTER，只能重建表。
   第一次写迁移时忘了关闭外键，`DROP TABLE activities` 直接报约束错误；改成
   "PRAGMA foreign_keys=OFF → 建新表 → 拷数据 → 删旧表 → 改名" 才对。
2. 老库升级后演示账号 `grade` 是 NULL，年级限定活动变成"谁都报不了"，演示很别扭；
   于是加了一步"只对演示账号 S001–S003 且值为 NULL 时回填年级"的幂等维护。
   这算是本次唯一的返工，也暴露了"加列"与"迁移数据"是两件事。
