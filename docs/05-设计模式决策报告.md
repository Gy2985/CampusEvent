# 实验二 · 设计模式决策报告

> 本报告回答三个问题：**哪里会变、用什么模式承接变化、为此付出了什么成本**。
> 所有结论都能在代码与测试中找到对应证据，不以“用了设计模式”本身作为结论。

## 1. 先识别变化点（而不是先选模式）

| 变化点 | 变化频率 | 影响面（若不隔离） | 结论 |
| --- | --- | --- | --- |
| 报名规则（直接报名、审核、将来的抽签/邀请制） | 高（需求变更最常打这里） | 报名主流程、状态判断、页面 | 需要稳定抽象 → **策略模式** |
| 通知渠道（站内消息、将来邮件/短信/微信） | 中 | 报名业务的事务代码 | 需要解耦 → **观察者模式** |
| 名额上限、重复报名、活动时间 | 低（属通用约束） | 所有活动类型 | **提取为服务层公共规则**，不抽象 |

这张表说明：两个模式不是“为了用而用”，而是分别承接两类真实的可变点；
而名额等稳定规则反而**不应该**被放进策略，否则每个策略都要重复实现。

## 2. 策略模式：让报名规则可替换

### 2.1 结构

| 角色 | 类 | 说明 |
| --- | --- | --- |
| 抽象策略 | `RegistrationPolicy` | 只有 `decide(context)` 与一个声明式属性 |
| 具体策略 | `DirectRegistrationPolicy`、`ApprovalRegistrationPolicy` | 分别返回“已通过”“待审核” |
| 上下文 | `RegistrationContext` | 活动、学生、已通过人数、当前时间（只读） |
| 决策结果 | `RegistrationDecision` | 目标状态 + 给学生的一句话文案 |
| 选择机制 | `PolicyRegistry` | 按 `activity.policy_type` 取实现 |

关键代码（`services/registration_service.py`）：

```python
policy = self.policies.get(activity.policy_type)      # 只知道抽象
context = RegistrationContext(activity, student, approved_count, current)
if policy.requires_immediate_capacity_check and context.is_full:
    raise CapacityExceededError(...)                    # 公共规则
decision = policy.decide(context)                       # 变化的部分
registration = registrations.create(..., status=decision.status)
```

**验收方式**：全项目检索 `policy_type ==`，只剩两处——注册表的键查找、活动表单的枚举校验；
业务主流程中没有任何“如果活动是审核型就……”的分支。

### 2.2 名额检查属于公共规则还是策略责任？

**结论：名额检查是公共规则，放服务层；策略只声明“要不要立即检查”。**

理由：

1. **语义相同**：无论哪种报名方式，“已通过人数不得超过上限”都成立，不是某个策略的业务特性。
2. **避免重复**：若放进策略，两种策略各写一遍，将来第三种策略还要再写一遍；一旦口径调整（例如“候补名额”），要改多处。
3. **保留差异**：两类活动确有差异——直接报名必须在提交时拦住，审核型允许排队、由批准时拦住。
   这个差异用一个布尔属性表达，比把整段判断复制到策略里更小、更可读。
4. **可测**：`X9` 用例专门验证“待审核不占名额、满员仍可申请”，`C8` 验证“批准时满员则失败”。
   如果规则放在策略里，这两条测试会分别散落在两个策略的测试中，容易漏。

### 2.3 新增一种报名方式要改哪里（扩展成本）

以“限额抽签”为例，三步：

1. 新增 `LotteryRegistrationPolicy(RegistrationPolicy)`，`decide` 返回“待审核”或新增状态；
2. 在 `build_default_registry()` 中 `register`；
3. 活动表单与 `PolicyType` 枚举各加一个取值。

`RegistrationService`、`EventBus`、页面路由、测试夹具都**不需要改动**——
这是策略模式在本项目里唯一值得声称的收益。

## 3. 观察者模式：让通知机制可替换、可失败

| 角色 | 类 | 说明 |
| --- | --- | --- |
| 事件 | `RegistrationEvent` | 已发生的事实：类型、报名ID、学生、文案、幂等键 |
| 主题 | `EventBus` | `subscribe` / `publish`，隔离单个观察者异常 |
| 观察者 | `NotificationObserver` | 写站内消息；失败则写留痕表 |

**三个必须回答的问题（对应设计任务 C）：**

1. **通知失败是否影响报名事务？**
   不影响。顺序是「业务事务 COMMIT → 发布事件 → 观察者写消息」。
   报名记录已落库，通知失败只写 `notification_failures` 并把异常记入日志。
   证据：`X13`（强制 `MessageRepository.add` 抛异常后，报名仍为“已通过”，留痕表多 1 条）。

2. **如何避免重复通知？**
   `dedupe_key = 事件类型:报名ID` 作为 `messages.dedupe_key` 唯一索引，
   写入用 `INSERT OR IGNORE`。即使同一事件被重复发布（重试、页面重复提交），
   也只会留下一条消息。证据：`X12`。

3. **为什么不用消息队列？**
   实验边界明确“无须引入消息队列”。单机同步分发已满足需求，
   引入 MQ 会把“事务与投递”的一致性变成分布式问题，收益与课程目标不匹配。

## 4. SOLID 对照

| 原则 | 本项目的体现 | 反例（如果没有这么做） |
| --- | --- | --- |
| S 单一职责 | 实体只存数据；策略只决定状态；观察者只管通知；服务只管编排与事务 | 把通知直接写进 `register()`，服务会同时承担业务与投递 |
| O 开闭原则 | 新增策略/观察者靠注册，不改主流程 | 主流程里的 `if 活动类型` 每加一种就要改一次 |
| L 里氏替换 | 任何 `RegistrationPolicy` 子类都满足 `decide` 的契约（返回合法状态） | 子类返回“已取消”这类非法初始状态会破坏服务层假设 |
| I 接口隔离 | 策略接口只有 1 个方法 + 1 个属性；仓储按表拆分 | 把“查活动+报名+发通知”塞进一个 God Service |
| D 依赖倒置 | 服务依赖 `RegistrationPolicy` 抽象，实现由注册表注入 | 服务直接 `new DirectRegistrationPolicy()`，测试无法替身 |

## 5. 成本：模式带来的复杂度（如实报告）

| 维度 | 不用模式（if-else + 直接写通知） | 本项目 |
| --- | --- | --- |
| 文件/类数量 | 约 4~5 个文件 | 领域、策略、事件、观察者、仓储、服务、Web 共 20 余个模块 |
| 首次理解成本 | 低，一个 `register()` 能读完 | 需要在 3~4 个文件之间跳转才能看全流程 |
| 新增报名方式 | 改主流程 + 改页面 + 补测试 | 加一个策略类 + 注册一行 |
| 换通知渠道 | 改业务代码（高风险） | 新增一个观察者并 `subscribe` |
| 通知失败的处理 | 通常“写日志了事”，无结构化记录 | 有 `notification_failures` 表，可补发 |

结论：**本项目规模下，模式确实让结构变复杂**（类数量翻倍、调用链变长），
收益主要体现在“需求变更时的修改范围”而不是“当前代码量”。
是否值得，要看变更的频率与影响面——这正是实验二希望通过 CR 变更来验证的东西
（变更后的可维护性对照见 `07-回归测试表.md` 与第 5 节统计）。
